# GitHub App lane

Status: Proposed 2026-11-06, partly built. The operator accepted everything, gave sign-off on the new dependencies on 2026-11-07, and chose the widened permission set below. This flips to Accepted once the operator widens the App's granted permissions on GitHub (not done) and a live token confirms `metadata:read`. Built: the `github_app` kind in `fleet-core`, the installation id parser, key loading and JWT signing in `crates/fleet-server/src/cred/app_jwt.rs` (the key loads at startup and the release path signs with it), the installation token mint, response validation and revoke in `crates/fleet-server/src/cred/app_mint.rs`, the server config `FLEET_GITHUB_APP_ID` and `FLEET_GITHUB_APP_KEY_FILE` with startup key load, validation of the sealed value, the `github_app_mint` audit schema (migration 0033) with bounded columns and a u64 installation id check, and the `credentials.tombstoned_at` column with a trigger that blocks restoring a tombstone, enforced by the store's release and list queries. `PutCredential` and the web form save `github_app` for a user who holds `forge:github_app`; the installation id must parse as u64 (SEC-019). `VerifyCredential` mints once against the repository of the user's latest Job and replies with no token text. It takes the same gate as a release, except for the cap: an `attempt` row of scope `probe` committed before the mint under `FOR UPDATE` on the credentials row, the per-User rate limit (a probe counts toward it, and so do releases) and no per-Job cap, since a probe row never counts toward any Job's cap (migration 0035), and the `minted`, `failed`, `revoked` and `revoke_failed` rows. A refused revoke answers `valid: false`, like any mint failure. A user with no Job gets `FAILED_PRECONDITION`. The release reply carries `expires_at_ms` and the `GitIdentity` from `FLEET_GITHUB_APP_BOT_NAME` and `FLEET_GITHUB_APP_BOT_EMAIL`. fleetd consumes the wire kind `github_installation_token`: the credential holder takes the token as the git and `gh` token the way it takes a PAT, keeps `expires_at_ms`, and re-validates the `GitIdentity` with `BotIdentity::new` (SEC-006, SEC-012) before the clone. A missing or invalid identity, a token that does not start with `ghs_`, or a reply that holds both a PAT and an installation token fails the Job with a fixed reason. The agent environment and the fallback commit carry the bot identity in `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME` and `GIT_COMMITTER_EMAIL`, and the job redactor masks the held token. The `forge:github_app` capability is built: the migration 0034 CHECK, the grant and revoke page for every capability, and its put and release gate in `cred::store`. Release is built: `release_for_job` partitions the forge kinds so the App wins over the PAT, mints after the capability check and the transaction commit, writes use rows only after the mint succeeds, and fails with the fixed error `PRECONDITION_APP_MINT` on any other mint failure, with no PAT fallback (SEC-008); the reply carries the token under wire kind `github_installation_token`. The CLI credential commands are built. The runbook is `docs/github-app-runbook.md`, and `crates/fleetd/tests/daemon_jobs.rs` runs an App Job and a PAT Job end to end against a local git remote and a fake REST endpoint. A mint failure answers the server status `FAILED_PRECONDITION` with `github app token unavailable`, and a mint failure at the first fetch reports the generic `credentials could not be fetched`. Refresh is built: fleetd calls `GetJobCredentials` again when fewer than 10 minutes of the token remain, before a Push or Gh child, a mirror fetch and a broker `gh` call, with an injected clock. Each of the last two resolves the token through the refresh and a `TokenLease` on every call, never from a copy taken when the job was set up. The job redactor takes the new token in one update before the holder makes it readable, and keeps masking the old one (SEC-017). Refreshes serialize per Job. A refresh whose mint fails keeps the last good token until it expires and retries after 30 seconds. The server counts `attempt` rows of scope `job` per Job against `MAX_APP_MINTS_PER_JOB` (34, the 29 refreshes of a 24 hour Job plus the first mint plus a margin of 4) and past it answers `FAILED_PRECONDITION` with `PRECONDITION_APP_MINT_CAP`, which fails the Job or step with a fixed reason and no PAT fallback (SEC-011). The release read takes `FOR SHARE` on the Job row and `FOR UPDATE` on the credentials row. The server also counts the User's `attempt` rows of the last 60 seconds against `MAX_APP_MINTS_PER_USER_PER_MINUTE` (20) in the same transaction, and past it answers the same `PRECONDITION_APP_MINT_CAP` and writes a `denied` row with reason `user mint rate` (SEC-003). A `denied` row for a Job and scope is not written again while one with the same reason is younger than `DENIED_DEDUPE_SECS` (60). fleetd revokes the token a refresh replaced and the held token when the Job ends, on any path through `AgentRunner::end_job` (finish, cancel, failure, lease loss), on its own task and best effort with `DELETE /installation/token`, bounded by `REVOKE_TIMEOUT` (10 seconds); a failed revoke logs a fixed string and never fails the Job (SEC-010). Every mint writes `github_app_mint` rows: `attempt` committed before the mint under `FOR UPDATE` on the credentials row (SEC-021, SEC-022), then `minted` with `expires_at` (SEC-023), `failed` or `denied`, and `revoked` or `revoke_failed` when the post-mint recheck revokes the token (SEC-005, SEC-015). A drop guard revokes a token whose release or verify future is cancelled after the mint. The guard stays armed until the revoke await finishes, so a cancel during the revoke writes a `revoke_failed` row. A guard dropped outside a runtime logs an error and cannot revoke. A second guard closes the `attempt` row as `failed` with reason `mint cancelled` when the release or verify future is dropped before the mint returns; the row still counts toward the per-Job cap and the per-User rate, because GitHub may have created the token. The installation lookup and the mint share one budget, `MINT_BUDGET` (7 seconds), and `MINT_HEADROOM` (3 seconds) is what remains of `fleet_proto::CALL_BUDGET` (10 seconds), the channel timeout fleetd sets and the deadline tonic enforces on the handler, so the server gives up and writes `failed` before the client does. fleetd derives `REQUEST_TIMEOUT` from the same constant, and `CALL_BACKSTOP` is one second more. fleetd revokes an installation token that sits in a reply it rejects (identity missing or invalid, malformed, a refresh that cannot swap), and a refresh that finds the entry replaced by a re-fetch for the same Job id (a different turn lock) revokes the token it minted and stores nothing. The rate window counts with `clock_timestamp()`, and the post-mint recheck re-reads `tombstoned_at`. Deleting a credential with mint history sets the tombstone in one transaction under `FOR UPDATE`, and a credential without history is deleted. `PutCredential` on a tombstoned row is refused with `PRECONDITION_CREDENTIAL_TOMBSTONED`. Startup config makes both key file paths absolute, requires `FLEET_MASTER_KEY_FILE` when the App is set, refuses a key file owned by another uid, and refuses an App key that `GET /app` shows belongs to another App id (an unreachable GitHub logs a warning and the check is skipped). The job redactor of an App Job also masks any `ghs_` token by shape, so a token the exact list has not seen is masked too (see Redaction below). A replaced token stays live until every Push or Gh child that started with it has exited, up to 15 minutes (`DRAIN_LIMIT`). The first fetch refuses a reply whose installation token has no expiry. A fresh token that looks expired or inside the 10 minute window is kept and marked skewed: it counts as usable for 50 minutes after it was fetched (`REFRESH_SKEW_MS` plus `REFRESH_SKEW_SLACK_MS`), the next refresh waits 45 minutes (`REFRESH_SKEW_MS`), a failed refresh past the 50 minutes fails the step with the `credential expired` reason, and a recorded wait more than 45 minutes ahead of the clock is ignored. A refresh answered with `PRECONDITION_APP_INSTALLATION` or `PRECONDITION_APP_REPO` is terminal: the step fails with that reason and the held token is not kept. A refresh that fails for good during the CI watch ends the watch as `Watched::Failed`: the Job fails with that reason and never with the shutdown reason. The installation and repository allowlists and the owner binding are built in `crates/fleet-server/src/cred/app_policy.rs` and `cred::store` (SEC-001, SEC-002, SEC-009, SEC-013, SEC-014). The server config adds `FLEET_GITHUB_APP_ACCOUNT` (required with the App), `FLEET_GITHUB_APP_INSTALLATIONS` and `FLEET_GITHUB_APP_REPOS`; an unset list allows nothing, and a repository entry whose owner is not the account refuses start. `PutCredential` and every release and verify refuse an installation that is off the list with `PRECONDITION_APP_INSTALLATION`, and the Job repository is compared in full as lowercase `owner/name` against the repository list with `PRECONDITION_APP_REPO`, both before any GitHub call. `PutCredential` and the mint then call `GET /app/installations/{id}` through the `InstallationDirectory` seam and refuse an installation that is suspended, belongs to another App id, belongs to another account or answers another id (`PRECONDITION_APP_INSTALLATION`); a failed lookup or an incomplete reply is a failed mint. Refusals at release and verify write a `denied` row. The shape of the `GET /app/installations/{id}` reply (`id`, `app_id`, `account.login`, `suspended_at`) is unverified against a live GitHub response. Not built: the per-credential repository list an admin sets (SEC-009 and SEC-002 name it; only the operator ceiling is enforced), the audit of revokes inside the mint client, a fleetd revoke that survives a daemon exit, and a revoke of a token GitHub created while the mint call was cut off, which nothing can revoke because its value was never read. SEC-002 is enforced at verify and release only: neither `PutCredential` nor Job submit checks the repository allowlist. Builds on ADR-0033, ADR-0040, ADR-0043, ADR-0045 and ADR-0054. Amends ADR-0024, ADR-0033, ADR-0040, ADR-0043, ADR-0045 and ADR-0054.

Jobs push and open pull requests with the owner's `github_pat` (ADR-0043), so every change appears under the owner's name and the token lives for weeks. This ADR adds a second GitHub path: a GitHub App installation. The Job gets a one-hour installation token scoped to its repository and acts as the App's bot identity.

## Decision

### Credential kind `github_app`

- `github_app` is a new Credential kind, stored per User. Its sealed value is the installation id and nothing else (ADR-0040 sealing, `static_secret` shape).
- The App id and the App private key are operator config on the server: `FLEET_GITHUB_APP_ID` and `FLEET_GITHUB_APP_KEY_FILE`. The key file is mounted from a Kubernetes Secret, like the master key (ADR-0040). The key never enters the sealed store and is never an environment variable.
- The bot name and the bot email id are server config as well: `FLEET_GITHUB_APP_BOT_NAME` and `FLEET_GITHUB_APP_BOT_EMAIL` are required with the App, and the server validates them by the identity grammar (SEC-006). They travel to the Box with the credential as `GitIdentity` (a name and an email).
- The wire kind `github_installation_token` is what the Box receives. It is not a stored kind: `PutCredential` refuses it.

### Selection

- When a User holds both `github_app` and `github_pat`, the App wins.
- A User with neither still fails with the fixed missing-GitHub error of ADR-0033.

### Capability

- `forge:github_app` is a new capability under ADR-0054. The server checks it at `PutCredential` for the `github_app` kind and again live at release, in the same transaction as the other release checks. A revoke refuses a leased Job that has not yet fetched its credentials.
- Escalation note: any holder of the capability can mint write tokens for any repository in the installation. The clamp below narrows each token to the Job repository, and the User chooses that repository at submit. The capability therefore grants write on every repository the installation covers. Admins grant it with that in mind.

### Minting

- The server signs a JWT with RS256 through `ring`, as a new direct `ring` dependency of the server crate (see SEC-018): `iat` is now minus 60 seconds, `exp` is now plus 540 seconds, `iss` is the App id (JWT rules: https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-json-web-token-jwt-for-a-github-app, official docs). It calls the installation token endpoint with that JWT (https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app, official docs: the token lasts one hour and the response carries `token`, `expires_at`, `permissions` and `repositories`).
- The request body comes from server constants only: `{"repositories":[<job repo name>],"permissions":{"contents":"write","pull_requests":"write","checks":"read","statuses":"read"}}`. No client field reaches it.
- The server fails closed on the response when any of these holds: the returned permissions are not a subset of the accepted set (SEC-016), `repositories` is not exactly the one requested, or `expires_at` is more than `MAX_TOKEN_TTL_SECS` away. The server pins `MAX_TOKEN_TTL_SECS` at 65 minutes as a named constant.
- The mint call runs outside the database transaction, after the capability check. The `attempt` row and the per-Job cap counter are written inside the transaction before it (SEC-005 and SEC-011). The token reaches fleetd and git as SEC-017 describes.
- The repository at mint comes from the stored Job row, never from a request field (SEC-009).

### Lifetime and refresh

- A token lasts one hour. fleetd refreshes it through `GetJobCredentials` when under 10 minutes remain, before a Push or Gh child, a mirror fetch or a broker `gh` call. A reply with no `expires_at_ms` fails the Job at the first fetch. A fresh token that already looks expired, or inside the 10 minute window, means the box clock runs ahead of the server's: fleetd keeps the token for 50 minutes after the fetch, fails the step with `credential expired` if the refresh still fails past that, and refreshes again only after 45 minutes. A box clock that runs behind the server's cannot be detected, and the step that uses an expired token fails at GitHub. A Push or Gh child fails the step when the refresh fails for good (per-Job mint cap, lost lease, installation or repository refusal), and the CI watch and the pull request lookup report that failure and never read it as a pending check or a missing pull request.
- Redaction: the redactor of an App Job holds the exact values and also masks any `ghs_` token by shape (`Redactor::with_installation_tokens`). fleetd keeps the shape rule on a merged copy per refresh, with no shared handle, so a copy made before a refresh still masks the new token.
  - History: `Redactor` is immutable, so `Redactor::merged` was added in 2995063 and the runner keeps one `Arc<Redactor>` per Job in `job_redactors`, dropped in `end_job`. `Redactor::with_installation_tokens` came in 7578b3c as the shape rule, and `AgentRunner::mask_refreshed` in `crates/fleetd/src/runner/token.rs` came in 6059f17: it replaces the entry with `merged(&fresh.redactor())` in one update under the map mutex. A copy made before a refresh holds only the old value and masks the new token by shape (doc comment on `with_installation_tokens`). A shared redactor handle was the alternative.
  - Cost: any `ghs_` string of 16 or more token characters is masked, whether or not it is the Job's token.
- The server caps mints per Job with a named constant. A Job over the cap fails.
- Agent-driven refresh is bounded by the cap and the per-User rate limit (SEC-011). Under the direct launcher the agent shares fleetd's uid (ADR-0024) and holds the token. Under the systemd launcher the broker (ADR-0037) holds the token and the agent holds none (ADR-0031), with no fleetd token and no network route to the server, so it cannot call `GetJobCredentials`.

### Identity on the Box

- fleetd re-validates the `GitIdentity` name and email grammar before use and fails the Job before clone on a bad identity. The server is not trusted alone, as in ADR-0054.
- A PAT Job keeps the fixed `JOB_NAME` and `JOB_EMAIL` in `crates/fleetd/src/agent_config.rs`. An App Job takes the identity from `GitIdentity` for the four `GIT_AUTHOR_*` and `GIT_COMMITTER_*` variables. The job `.gitconfig` still names the fixed identity, and the variables take precedence.
- Bot id lookup, for the operator: `gh api /users/<slug>[bot] --jq .id`.

### Failure

- A mint failure at the first fetch fails the Job; a refresh whose mint fails keeps the last good token until it expires. The server answers `FAILED_PRECONDITION` with `github app token unavailable`, and fleetd reports `credentials could not be fetched`. There is no fallback to a PAT or any other identity (ADR-0033).

### Security decisions

- SEC-001, installation allowlist: the operator sets `FLEET_GITHUB_APP_INSTALLATIONS`, a list of allowed installation ids. At `PutCredential` and again at mint the server calls `GET /app/installations/{id}` with the App JWT. It refuses unless the id is on the allowlist, `account.login` matches the operator account, `suspended_at` is null and `app_id` equals the configured App id (SEC-013). The App must be private, installable only on the operator account.
- SEC-002, repository allowlist (built: operator ceiling only, see Status): each `github_app` credential carries a repository allowlist. `PutCredential` checks the installation allowlist only. The repository allowlist is enforced when a credential is verified and when it is released, since only then is a Job repository known. Until the allowlist is set the server refuses every installation and every repository. Multi-user rollout requires branch protection on every installed repository.
- SEC-003, rate limit: the server applies a per-User mint rate limit (see SEC-004 and SEC-011). The limit is the named constant `MAX_APP_MINTS_PER_USER_PER_MINUTE`. The database enforces it by counting `github_app_mint` rows, so it holds across replicas. The count and the `attempt` insert run in one transaction that takes `FOR UPDATE` on the credentials row (SEC-021), so concurrent releases for one User serialize. A breach writes a `denied` row and returns `FAILED_PRECONDITION` with `PRECONDITION_APP_MINT_RATE` (`github app token rate limited`), which is retryable and distinct from `PRECONDITION_APP_MINT_CAP`, the terminal per-Job cap. The limit lifts within a minute, so fleetd treats the rate answer as transient: the first fetch asks again up to 7 times, 10 seconds apart (70 seconds in all, longer than the one-minute window), then fails the Job with `github app token rate limited`, and a refresh keeps the held token and retries after 30 seconds. The denied attempts do not count toward the limit, so waiting does not extend it. There is no PAT fallback.
- Probe scope: `github_app_mint.scope` is `job` (default) for a release or refresh and `probe` for `VerifyCredential`. Only `job` rows count toward the per-Job cap and toward the dedupe of `denied` rows; every `attempt` row counts toward the per-User rate. A probe keeps the latest Job's id and repository in its row for audit, so a probe against a Job near its cap can neither starve that Job's refresh (which has no PAT fallback) nor be starved by it. A separate probe cap is not added: the per-User rate already bounds probes. Rows written before migration 0035 carry `job`; old probe rows cannot be told apart from job rows, so they stay in the per-Job count of their Job. They leave the per-User rate count after the one-minute window. A nullable `job_id` was rejected: it would need a CHECK and trigger rewrite and break the audit join on `job_id`.
- SEC-004, refresh: every refresh re-checks the capability, requires the Job to be running and leased to the calling Box, then mints (SEC-011). The mint cap is `max_job_duration / refresh_interval` plus a margin.
- SEC-005, audit: `credential_use` stays insert-only (trigger in migration 0017) and keeps one row per credential released (ADR-0033), unchanged. Mint audit goes into a new insert-only table `github_app_mint` (migration 0033) with a trigger rejecting `UPDATE`, `DELETE` and `TRUNCATE`. Columns: `id`, `mint_id`, `attempt_id`, `credential_id`, `job_id`, `repo`, `installation_id`, `requested_permissions`, `outcome`, `reason`, `expires_at`, `at`, `scope` (added by migration 0035; `mint_id` and `attempt_id` as SEC-015 defines them, `expires_at` nullable and recorded on `minted` rows only, as SEC-023 defines it). The outcome set is `attempt`, `minted`, `failed`, `denied`, `revoked` and `revoke_failed` (SEC-022). The table is append-only. Each refresh release writes one `credential_use` row per credential released, the ADR-0033 rule, as `crates/fleet-server/src/cred/store.rs` does today: the release transaction inserts one row for each released credential, so a refresh adds a row in addition to its `github_app_mint` rows. Inside the transaction and before any mint call the server inserts an `attempt` row. If that insert fails there is no mint call (fail closed). The result is a second row with outcome `minted`, `failed` or `denied`, with a reason code and no secret. A capability or allowlist denial writes a `denied` row. An `attempt` with no outcome row after `MAX_TOKEN_TTL_SECS` reads as unknown by query, never by update.
- SEC-006, identity grammar: the name matches `\A[A-Za-z0-9](?:[A-Za-z0-9 ._\[\]-]{0,62}[A-Za-z0-9\]])?\z`, so it starts with an alphanumeric and cannot end in a space (SEC-012). The email matches `\A[0-9]+\+[a-z0-9-]+\[bot\]@users\.noreply\.github\.com\z` and is at most 128 bytes. The uppercase rejection applies to the email only. Hostile-input table, all rejected: CR, LF, NUL, angle brackets, U+2028, NEL, over-length, non-ASCII, plus the SEC-012 additions.
- SEC-007, runbook: rotate the App key by adding a second key on GitHub (it supports several), switching `FLEET_GITHUB_APP_KEY_FILE`, then deleting the old key. The server refuses a key file that group or other can access (mode & 0o077 must be 0), refuses a path that is not a regular file, and follows symlinks because Kubernetes Secret mounts are symlinks. The server refuses a key file owned by another uid than its effective uid (enforced in `AppKey::load`), and the mode check leaves no one else write access. The server reads it into a `Zeroizing` buffer, implements `Debug` with redaction, and logs only fixed error codes.
- SEC-008: a User who holds a `github_app` credential but lacks `forge:github_app` fails the Job: the server answers `PERMISSION_DENIED` and fleetd reports `credentials refused: lease does not match`. The server never falls back to the PAT.
- SEC-009, allowlist authority and grammar: only an admin or operator config sets the allowlist, never the credential owner. Built: the operator ceiling `FLEET_GITHUB_APP_REPOS` alone is the effective list. Not built: a per-credential list an admin sets, which would narrow the ceiling by intersection. An entry is exact `owner/name` or `owner/*`, with no other glob. The server compares after ASCII lowercasing. Hostile-input table, all rejected: `..`, an extra slash, an empty label, a trailing slash, whitespace, non-ASCII, a backslash. The repository at mint comes from the stored Job row, never from a request field.
- SEC-010, revocation: the server never stores the token, so it runs no sweep. The server sends `DELETE /installation/token` immediately on any failed response validation, before it discards the token. fleetd revokes the old token after a successful refresh, and makes a best-effort revoke at Job end, cancel, failure and lease loss. The revoke of a replaced token waits until every Push or Gh child that started with it has exited, up to 15 minutes, because the child keeps the old value in its environment. A second fetch for an id fleetd already holds revokes the held token first. A refresh refused with `PRECONDITION_APP_INSTALLATION` or `PRECONDITION_APP_REPO` is sticky for the Job: fleetd records the refusal, returns it on every later refresh with no new fetch, and never hands the held token out again. The broker `gh` call and the mirror fetch resolve the token on every call and hold a lease on it until the child exits, so a refresh never revokes a token under them. A response with no usable token has no revoke. A 201 body that does not parse but whose `token` field reads is still revoked; a duplicated `token` key reads as no token. Residual: a 201 body over `MAX_RESPONSE_BYTES` is not revoked, because the token may sit past the cap, and the one-hour expiry bounds it. Residual: when fleetd cannot revoke (crash, lost network), the one-hour expiry is the only bound. Residual: when the mint call is cut off after GitHub created the token (the server budget, a dropped handler or a lost connection), nothing holds the value and nothing can revoke it, so the one-hour expiry is the only bound. The server writes `attempt` then `failed` with reason `mint cancelled` or `mint failed` for it, and the attempt keeps its slot against the cap. A refresh that fails for a transient reason retries after 30 seconds and spends another slot.
- SEC-011, mint ordering: the `attempt` row and the per-Job cap counter increment happen inside the transaction with a row lock on the Job row and `FOR UPDATE` on the credentials row (SEC-021), then the mint runs. After the mint the server re-checks the Job state. If the Job ended or the capability is gone, it revokes the token and returns `PERMISSION_DENIED`. The wire text is `lease does not match` for a lost lease or the text of the constant `ERR_CAPABILITY_NOT_GRANTED` (`credential kind needs a capability the user lacks`) for a lost capability. It is never the text of the constant `PRECONDITION_APP_MINT` (`github app token unavailable`). The recheck also re-reads the capability (SEC-017). Under the direct launcher the agent shares fleetd's uid (ADR-0024) and can drive refresh, bounded by the cap and the per-User rate limit. Under the systemd launcher the broker holds the token and the agent holds none (ADR-0031, ADR-0037).
- SEC-012, identity injection: the identity name must start with an alphanumeric. Patterns are anchored with `\A` and `\z` in both the name and the email. fleetd passes the identity by environment or `git -c`, never as a bare argv token. The hostile table adds leading whitespace and trailing whitespace for the name, and uppercase for the email only.
- SEC-013, key and installation checks: the server holds the parsed key in one process-lifetime object with a redacted `Debug`. Residual: the key stays in process memory for the life of the server. At `PutCredential` and at mint the `GET /app/installations/{id}` response must have `suspended_at` null and `app_id` equal to the configured id.
- SEC-014, owner binding: the installation `account.login`, ASCII-lowercased, must equal the operator account at `PutCredential` and at mint, and the Job repo owner must equal it when a credential is verified or released. The operator account is config `FLEET_GITHUB_APP_ACCOUNT`. Allowlist and ceiling entries whose owner differs from it are rejected at config load. `FLEET_GITHUB_APP_REPOS` unset means deny-all.
- SEC-015, correlation: every `github_app_mint` row carries `mint_id` (uuid). Outcome rows reference the attempt through `attempt_id`, with a unique `(attempt_id, outcome)`. The `credential_id` foreign key is `ON DELETE NO ACTION`. If the outcome insert fails after a successful mint, the server revokes the token and returns the storage error (`UNAVAILABLE`), not the fixed mint error (built in `cred::store`: the verify path revokes before it reports the failed outcome write, and the release path revokes best effort when its second transaction fails).
- SEC-016, response validation: the accepted response permissions set is `{contents:write, pull_requests:write, checks:read, statuses:read, metadata:read}`. The response must be a subset: a missing key or a lower level passes, any other key or a higher level fails closed and triggers the SEC-010 revoke. An already expired token (`expires_at` at or before now) is refused as an expiry failure. Inferred, not part of the design: GitHub adds `metadata:read` to every installation token, so the set includes it. Still open: confirm with a live token that GitHub returns `metadata:read` (`METADATA_PERMISSION` in `app_mint.rs` is the single place to change).
- SEC-017, recheck and token handling: the post-mint recheck (SEC-011) also re-reads the capability. In fleetd the token never reaches argv, `.git/config` or logs. SEC-023 states which processes hold it in their environment and which receive it through askpass.
- SEC-018, dependencies: `ring` 0.17.14, `pem` 4.0.0, `zeroize` and `serde` (workspace) are direct dependencies of the server crate. `pem` parses the PEM wrapper. `ring` takes PKCS#1 DER (`RSA PRIVATE KEY`) and PKCS#8 DER (`PRIVATE KEY`). `ring` and `pem` came with `app_jwt.rs`, and `rustix` is a workspace dependency (`Cargo.toml`, version 1.1.5 in `Cargo.lock`, features `process` and `fs`) that the server crate now uses too (`crates/fleet-server/Cargo.toml`). The operator gave sign-off on all three on 2026-11-07.
  - `ring` 0.17.14, licence Apache-2.0 AND ISC (https://crates.io/api/v1/crates/ring, registry metadata). It signs: `AppKey::sign` in `crates/fleet-server/src/cred/app_jwt.rs` calls `RsaKeyPair::sign` with `RSA_PKCS1_SHA256`, which is RS256, and `AppKey::load` builds the key pair with `RsaKeyPair::from_der` (PKCS#1) or `RsaKeyPair::from_pkcs8` (PKCS#8). `ring` has no PEM parser, so it needs `pem`. The server crate takes the default features. Advisory status: the RUSTSEC-2025-0007 hiatus advisory was withdrawn after the rustls team got access (https://rustsec.org/advisories/RUSTSEC-2025-0007.html, advisory database).
  - `pem` 4.0.0, licence MIT (https://crates.io/api/v1/crates/pem, registry metadata). `AppKey::load` calls `pem::parse` on the key file bytes and takes `tag()` and the DER contents, then matches the tag against `RSA PRIVATE KEY` or `PRIVATE KEY` and refuses any other. `pem` does no ASN.1 validation: `ring` rejects a malformed DER at `from_der` or `from_pkcs8`, and both failures map to `AppKeyError::Key`. The claim that `pem` does no ASN.1 validation rests on this reading of the code and was not checked against the crate source (unverified).
  - `rustix` 1.1.5, licence Apache-2.0 WITH LLVM-exception OR Apache-2.0 OR MIT (https://crates.io/api/v1/crates/rustix, registry metadata, 1.x). The server calls one function: `rustix::process::geteuid()` in `AppKey::load`, which passes the effective uid to `AppKey::load_as`. `load_as` compares it with the key file's owner from `std::fs::Metadata::uid` and refuses a mismatch with `AppKeyError::Owner` (SEC-007). The mode check uses `std` `PermissionsExt`, not `rustix`. There is no direct `libc` dependency or `unsafe` block in this repo for the uid lookup.
- SEC-019, installation id and URL construction: the installation id must parse as `u64` at `PutCredential`, and the server rejects anything else. The server builds every URL from the parsed integer, never from the stored text. The mint body is built with `serde_json` from the stored Job repo name, whose grammar is SEC-009. Hostile-input table, all rejected: `/`, `..`, `?`, `#`, `%2f`, leading zeros, over-long.
- SEC-020, outbound client: the base URL is the fixed `https://api.github.com` with no production environment override. Redirects are disabled. The connect timeout and the total timeout are named constants. The server reads the response with `take(cap + 1)` and a named cap, and fails closed on truncation. The JWT type and the installation token type implement `Debug` with redaction and hold their value in `Zeroizing`, on the server and in fleetd.
- SEC-021, credentials row lock: the per-User rate limit (SEC-003) and the per-Job cap (SEC-011) take `FOR UPDATE` on the credentials row in the same transaction as the count and the `attempt` insert. Without the lock two concurrent releases both read a count under the limit and both insert.
- SEC-022, commit order and credential deletion: the `attempt` row commits first, then the mint runs, then the outcome transaction commits. The outcome set adds `revoked` and `revoke_failed`, which record the SEC-010 revoke and its failure. A credential with mint history cannot be deleted: a trigger and the `ON DELETE NO ACTION` foreign key (SEC-015) refuse it. Off-boarding therefore uses capability revocation and a tombstone column on `credentials`. The tombstone is built. `CredentialStore::delete` sets the tombstone for a credential with mint history and does not delete the row. A tombstoned credential is never released, never probed and never overwritten by a put.
- SEC-023, residual token lifetime and token handling: When fleetd's revoke at Job end fails (SEC-010), a refresh-minted token can outlive the Job by up to one hour, because the server never stores the token and cannot revoke it later. The same bound covers a token in a 201 body over `MAX_RESPONSE_BYTES`, which the server does not revoke. The server records `expires_at` on minted rows in `github_app_mint`, so the overlap is auditable by query. Token handling in fleetd, from ADR-0024, ADR-0037 and `crates/fleetd/src/runner/token.rs` and `crates/fleetd/src/broker.rs`: `GH_TOKEN` is in the environment of the `git push` child, the `gh` child (with `GH_ENTERPRISE_TOKEN` off `github.com`) and the mirror fetch child, and `fleetd askpass` prints it from its own `GH_TOKEN` for a password prompt. The `git` process in those children receives the token through askpass and never in argv. The agent child environment strips `GH_TOKEN`. Under the direct launcher the agent shares fleetd's uid and reads the token from `/proc` (ADR-0024 Known limit). Under the systemd launcher the broker (ADR-0037) performs push and `gh` calls and the agent holds no token.

### Permission set

The requested permission set is a server constant: `contents:write`, `pull_requests:write`, `checks:read` and `statuses:read`. The operator chose this widened set; it first held only the two write permissions. Reading CI results needs the two read permissions, per https://docs.github.com/en/rest/overview/permissions-required-for-github-apps (official docs). Without them `pr_checks` and `ci_result` fail for App Jobs.

Operator action, not done: widen the App's granted permissions in the GitHub App settings to add `checks:read` and `statuses:read`. Inferred, not part of the design: GitHub refuses a token request for a permission the App does not hold, so mints fail until this is done.

Inferred, not part of the design: `gh pr checks` may use GraphQL, which has its own permission rules. Test with a live token.

A push that touches `.github/workflows` needs the `workflows` permission, which this ADR does not request. Such pushes fail.

## Consequences

- Pull requests and commits show the bot as author. Operators must create the App, install it and record the installation id and bot email id before any User can store the credential.
- `fleet credential list`, `put`, `delete` and `verify` cover every kind (`crates/fleet-cli/src/credential.rs`). The secret is read from stdin, never from an argument, and every server refusal prints a fixed notice shared with the web page (usage, I/O and connect failures keep their own error variants) through `fleet_proto::CredentialNotice`. The web form lists `github_app` for every user: a user without `forge:github_app` gets the capability notice on save, so the form is not hidden.
- Under the direct launcher ADR-0024 still applies: the agent runs as fleetd's uid and can read the token from `/proc`. Under the systemd launcher ADR-0031 supersedes that limit and the broker (ADR-0037) holds the token, so the agent holds none. The one-hour life and the one-repository clamp bound the damage.
- A Job needs one extra HTTPS call to GitHub at release and at each refresh. A GitHub outage fails new App Jobs.

## Considered and rejected

- **Store the App private key in the sealed store.** One store compromise would expose a key that mints tokens for every installation. Operator config keeps it out of the database and its backups.
- **Key in an environment variable.** Environment values leak through process listings and crash dumps.
- **PAT wins when both exist.** It would keep Jobs on the long-lived token the lane exists to replace.
- **Fall back to a PAT on mint failure.** It hides an outage and changes the acting identity without the User asking.
- **Client-chosen permissions or repositories.** The request would then be as wide as a client can ask.
- **Mint inside the release transaction.** A slow GitHub call would hold row locks.
