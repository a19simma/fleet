# T6: pueue callback on v4.0.4

Date: 2026-10-24. Box: <box>, pueue and pueued v4.0.4.

## Question

Does the pueue `callback` fire for tasks that succeed, fail and are killed? Which template variables exist? Does the callback receive output? What is the latency?

## Method

A separate pueued instance, so the shared daemon and its default group were untouched. Artifacts in `~/phase0/T6/` on the box: `pueue.yml`, `cb.sh`, `callback.final.log`.

```
pueued -c ~/phase0/T6/pueue.yml -d
pueue -c ~/phase0/T6/pueue.yml add -- '<cmd>'
```

Config (`pueue_directory`, `runtime_directory`, `unix_socket_path`, `pid_path` all under `~/phase0/T6`):

```
daemon:
  callback: '~/phase0/T6/cb.sh "{{ id }}" "{{ group }}" "{{ result }}" "{{ exit_code }}" "{{ start }}" "{{ end }}" "{{ path }}" "{{ command }}" "{{ output }}"'
  callback_log_lines: 10
```

`cb.sh` appends timestamp plus its nine arguments to `callback.log`. Tasks: success with stdout and stderr, `exit 3`, `pueue kill`, success in group `g6`, external `kill -9` of the task process.

## Results

Fired for every finished task: success, failed, killed by `pueue kill`, and killed from outside. Grouped tasks fire too (`group=[g6]`). A task rejected at `add` (bad `-w` directory) never became a task and fired nothing.

```
id=[0] group=[default] result=[Success] exit_code=[0] start=[1792836841] end=[1792836841] path=[/home/agent] command=[echo hello-out; echo err-out >&2; date +%s.%N] output_len=[38] output=[hello-out
err-out
1792836841.604439280]
id=[1] group=[default] result=[Failed] exit_code=[3] ... command=[echo failing; exit 3] output=[failing]
id=[2] group=[default] result=[Killed] exit_code=[None] start=[1792836845] end=[1792836860] ... command=[sleep 60] output_len=[0]
id=[5] group=[default] result=[Failed] exit_code=[137] ... command=[sleep 60] output=[Killed]     (external kill -9)
```

Variables confirmed: `id`, `group`, `result`, `exit_code`, `start`, `end`, `path`, `command`, `output`. `start` and `end` are unix seconds. `result` is `Success`, `Failed` or `Killed`. `exit_code` renders the string `None` for `pueue kill`. `output` is the last `callback_log_lines` lines of stdout and stderr merged. Only finished tasks fire: no queued or started callback exists.

Latency: task end at `...841.604`, callback line at `...841.907` (0.30 s). `pueue kill` issued at `...868.454`, callback at `...868.715` (0.26 s). External kill at `...891.379`, callback at `...891.595` (0.22 s).

Problem found: the template substitutes `{{ command }}` and `{{ output }}` raw into a shell string. A task command containing double quotes split the argv. Task `echo "quoted $HOME" 'x'; date` produced:

```
id=[3] ... command=[echo quoted] output_len=[28] output=[/home/agent 'x'; date +%s.%N]
```

This corrupts fields and is a shell injection path, since task commands and output are attacker-influenced by agent content.

## Result

Pass for firing and variables. Partial for safe use: command and output cannot be passed through the template.

## Plan impact

- The callback is a valid backstop for `pueue.task_finished`, and covers killed tasks (Killed, exit_code None) and externally killed ones (Failed 137).
- The callback must pass only `{{ id }}` and `{{ group }}` (and optionally `result`, `exit_code`, which are not free text). fleetd then fetches command, output and times through `pueue status --json` and the pueue log. Never place `{{ command }}` or `{{ output }}` in the callback string.
- Update plan line 146 from "Unverified" to verified, with this restriction. Treat `exit_code=None` as killed.
- Callback runs under the pueued process, so the fleetd subcommand it calls must be a fast fire-and-forget (write to a spool or local socket). Polling `pueue status --json` every 5 s stays as the reconcile path for callbacks lost while fleetd is down.
- The callback is configured in the shared `pueue.yml`, which needs a pueued restart to take effect. Provision it in the Box image, not at runtime.
- No queued or started callback: `pueue.task_queued` and `pueue.task_started` must come from polling or from `fleet-job`.
- Cleanup: own pueued stopped by pid file (`kill $(cat run/pueue_t6.pid)`), `run/` and `state/` deleted, no survivors. The shared daemon was unaffected.
