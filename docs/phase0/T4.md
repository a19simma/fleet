# T4. Managed settings on Linux

Result: Pass. `/etc/claude-code/managed-settings.json` loads on 2.1.289, and its hooks fire alongside user hooks and `--settings` hooks. The `managed-settings.d/*.json` drop-in loads too.

## Question

Does a hook in `/etc/claude-code/managed-settings.json` fire on Linux, and does it fire together with a hook in `~/.claude/settings.json`? Does a hook passed with `--settings` also fire? Does the `managed-settings.d` directory load?

## Setup

Box: <box>, Claude Code 2.1.289 (not upgraded), subscription auth via `/etc/swarm/box.env` and `/etc/swarm/secrets.env`. `ANTHROPIC_API_KEY` checked unset before each run (`API_KEY unset ok` printed by `run.sh`). Nothing was listed in `/etc/claude-code` before the test (the directory did not exist).

Files under `~/phase0/T4/` on <box>:

- `hook.sh <prefix> <event>`: `cat > ~/phase0/T4/<prefix>-<event>-$(date +%s%N).json`, so each hook writes its stdin payload.
- `managed.json`, `mdrop.json`, `flag.json`: `hooks` blocks with a `Stop` and a `UserPromptSubmit` command hook, using prefixes `managed`, `mdrop`, `flag`.
- `settings.json.bak`: byte copy of `~/.claude/settings.json` taken before the test.
- `run.sh <label> [extra claude args]`: clears old hook files, then runs `claude -p "reply with ok" --output-format json --debug-file <label>.debug </dev/null` in `~/phase0/T4/wd`, and lists the hook files written.

User settings: `~/.claude/settings.json` already had `Stop` with `workmux set-window-status done` (plus Notification, PostToolUse, PreToolUse, SessionStart, UserPromptSubmit). I merged my hooks with jq, appending a second entry to `.hooks.Stop` and `.hooks.UserPromptSubmit` that runs `hook.sh user <event>`:

```
jq --arg d "$D" '.hooks.Stop += [{hooks:[{type:"command",command:($d+"/hook.sh user Stop")}]}] | .hooks.UserPromptSubmit += [{hooks:[{type:"command",command:($d+"/hook.sh user UserPromptSubmit")}]}]' settings.json.bak > user.merged
```

Managed file installed with `sudo mkdir /etc/claude-code && sudo install -m 644 -o root -g root ~/phase0/T4/managed.json /etc/claude-code/managed-settings.json`. Listing: `-rw-r--r-- 1 root root 422 Oct 24 10:18 managed-settings.json`.

## Findings

(a) Managed and user hooks for the same event: both fire. Hooks merge across sources, managed does not replace user. The user's own `Stop` entry count was 2 in the merged file (workmux plus mine) and my user hook fired. Whether the original workmux command ran was not observed; it writes nothing I could capture, and the debug log shows no per-command line for it.

(b) `--settings <file>` hook: fires alongside the managed and user hooks (run B, all three prefixes present).

(c) Lockdown keys: not set, not tested. The docs (official docs, [managed settings](https://code.claude.com/docs/en/managed-settings.md)) list `allowManagedHooksOnly` ("When `true`, restricts which hooks run") under keys that apply "the strictest value any source sets". Because I did not set it, I did not observe its effect on 2.1.289. The first docs page I read, [settings](https://code.claude.com/docs/en/settings.md), says managed settings are top of the precedence stack and "Nothing in your own settings files or `--settings` overrides a managed key", which describes scalar keys; the hook arrays merged in practice. Unverified: that the lockdown key exists in 2.1.289 itself (docs are for the latest version).

(d) Path: the docs say `/etc/claude-code/managed-settings.json` on Linux and WSL, plus an optional `managed-settings.d/` in the same directory. Quote (official docs): "Claude Code merges `managed-settings.json` first, then every `*.json` file in the directory in alphabetical order... Claude Code ignores hidden files and files that don't end in `.json`." Observed: both the main file (run A, B) and the drop-in alone (run C) load on 2.1.289. I did not test both together or the ordering.

## Plan impact

- The first-choice design works: put the loopback http hook config in the Template at `/etc/claude-code/managed-settings.json`. It loads on Linux 2.1.289 at that path and merges with the user hooks, so the laptop's stowed `settings.json` carries no loopback hook and the Box-only stowed fragment is not needed.
- Precedence finding: hooks accumulate across managed, user and `--settings` sources. A user or Job `--settings` hook cannot remove or suppress the managed hook. Each event therefore fires every source's hooks, so fleetd must tolerate the same event arriving once per source and any user hook that also posts to fleetd would double count. Keep the loopback hook only in managed settings.
- A `managed-settings.d/10-fleetd.json` fragment is an equally good delivery path and keeps fleetd's file separate from other managed policy.
- T3 and T8 used `--settings`. T4 shows the same http hook shape works from either location (command hooks tested here; the http type in a managed file was not run).
- A parse error in a managed file stops Claude from starting (docs). Bake the file as valid JSON and check it in the Template build.
- Not tested: http hook type in managed settings, both managed file and drop-in together, interactive sessions, `allowManagedHooksOnly`.
