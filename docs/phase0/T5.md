## Field list against the plan

Plan list: status, status_ts, updated_ts, workdir, pane_pid, command, boot_id, agent_kind, agent_session_id, prompt, window_name, session_name.

All twelve exist. Extra fields: `pane_key` (backend, instance, pane_id), `activity_ts`, `pane_title`. Findings:

- `prompt` is `null` in every file, including right after `workmux add -p`. The plan's `prompt` field on `workmux.status_changed` carries nothing from workmux. An older swarm-scratch file shows `""`.
- `pane_pid` is the pane's login shell (`bash -l`), not claude. Claude is its child: `bash,130085 -l` then `claude,130099`. Use `pgrep -P <pane_pid> claude` to find the process.
- The file name is `tmux__<instance urlencoded>__<pane_id urlencoded>.json`, so the pane id is the identity, and a new agent in a new pane is a new file.
- `command` stayed `claude` after the process was killed.

## Kill test

Run A (t5-kill, first attempt): the agent went `working` to `done` within 4 s although `sleep 90` was still running in a child process (status `done` at 10:15:35, bash child alive at 10:15:43). The kill landed on a `done` agent, so this run proves little. Run B and C used a foreground sleep that kept status `working`.

Run B, `kill -9` on the claude pid (130099, child of pane_pid 130085) while `working`, no `wait` running:

```
kill_rc=0 at 10:16:18.551
{"status":"working","status_ts":1792836963,"updated_ts":1792836963,"pane_pid":130085,"command":"claude"}   # copied right after the kill
10:16:19 .. 10:16:28 exists   (polled each second with test -e, no workmux call)
tmux pane %22 still alive, pane_current_command: bash
workmux wait t5-kill --status done --timeout 30
  Error: No agent found matching 't5-kill'
  wait_rc=1
10:16:28.601 DELETE ...%2522.json
```

The file is not touched by the kill. It stays `working` and stale until any `workmux` command that reconciles runs, then it is deleted (here the `wait` call deleted it and exited 1 immediately). The same happened to the earlier stale files of removed worktrees: `workmux rm` leaves the file, and the next `workmux status --all` or `wait` deleted five of them at once (10:15:25.591 to .608). With no workmux call, the file lingered for as long as I polled (at least 10 s, unbounded in principle). `workmux status --all` never listed the killed agent: it prints only agents whose pane still runs the agent, and it deletes the stale file as a side effect.

Run C, `workmux wait` started 3 s before the kill:

```
workmux wait t5-kill --status done --timeout 50 &
kill -9 130561 at 10:16:51.250
t5-kill: agent exited unexpectedly
rc=3 at 10:16:52.276
10:16:52.274 DELETE ...%2524.json
```

Exit 3 confirmed, about 1 s after the kill. The wait process itself deleted the state file. The pane survived as a bash prompt, so "agent_gone" via pane_missing does not fire here.

## Plan impact

1. Crash detection by `workmux wait` works only if the child is already running when the agent dies. The plan's design (spawn `workmux wait <target>` for each agent in a working state) fits. Start it on the `working` transition and on watcher startup. A wait started after the crash exits 1 with "No agent found", which the watcher must treat as `agent_gone` or crashed-unknown, not as an error. Map: exit 3 gives `workmux.agent_crashed`; exit 1 right after spawn gives `workmux.agent_gone`; exit 0 is the status reached.
2. A killed agent emits no event of its own. The state file keeps `working` and does not change. The DELETE event that follows is caused by workmux commands (including the watcher's own 10 s `workmux status --all --json` reconcile and its `wait` children), so a delete while the agent was working means crashed or gone, and both signals can race. The watcher should dedupe `agent_crashed` and `agent_gone` per pane id and `status_ts`.
3. The inotify handler must listen for `delete` as well as `moved_to`. The plan says to react to create and rename-into events only. Add delete.
4. Drop `prompt` from the `workmux.status_changed` payload, or source it from the Job or fleet-side launch record. workmux stores null.
5. Use the pane id (file name) as the agent key, and `pane_pid` only as the parent of the claude process.
6. `status` can be `null` before the first hook. The watcher must accept it as a distinct pre-working state.
7. Do not rely on `status` being `working` while tools run: Run A showed `done` while a background-style tool call was still running.
8. `workmux rm` leaves stale files until the next reconcile, so cleanup of `agent_gone` for removed worktrees is delayed by at most one poll cycle in fleetd.
9. ReadWritePaths for the fleetd unit must allow writes to `~agent/.local/state/workmux` if the watcher runs `workmux status` or `wait`, because those commands delete stale files. Read-only is not enough (relevant to T9).
