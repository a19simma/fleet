# T9: system unit reaching pueue

Date: 2026-10-24. Box: <box>, systemd unit as `User=agent`, pueue v4.0.4.

## Question

Can a system unit with `User=agent` and `ProtectSystem=strict` run `pueue status --json` against the agent's real pueue socket and read `~/.local/state/workmux`? Is `XDG_RUNTIME_DIR` needed?

## Socket facts

From `~/.config/pueue/pueue.yml`: `use_unix_socket: true`, `unix_socket_path: /run/user/1000/pueue_agent.socket`, `unix_socket_permissions: 448` (octal 700).

```
700 agent:agent /run/user/1000/pueue_agent.socket
700 agent:agent /run/user/1000          (tmpfs, created by user@1000.service)
664 agent:agent /run/user/1000/pueue.pid
```

Only uid 1000 (and root) can connect. The socket sits inside `/run/user/1000`, which exists only while `user@1000.service` runs (linger is on). The path is absolute in the config, so it does not depend on `XDG_RUNTIME_DIR`.

## Method

Throwaway `/etc/systemd/system/fleetd-t9.service`, `Type=oneshot`, `User=agent`, `Group=agent`, `After=user@1000.service`, `NoNewPrivileges=yes`, `ProtectSystem=strict`, `ReadWritePaths=/home/agent/.local/state/workmux`, run once with no `XDG_RUNTIME_DIR` (A) and once with `Environment=XDG_RUNTIME_DIR=/run/user/1000` (B). `ExecStart=~/phase0/T9/t9.sh` runs `pueue --config ~/.config/pueue/pueue.yml status --json`, the same without `--config`, lists `~/.local/state/workmux/agents`, and tries writes. Journals: `~/phase0/T9/journal-A.log`, `journal-B.log` (B holds both runs). Unit removed afterwards.

## Results

Variant A (`XDG_RUNTIME_DIR=[unset] HOME=[/home/agent]`) and B (`XDG_RUNTIME_DIR=[/run/user/1000]`): both returned the live task JSON from the real daemon, with `--config` and without it.

```
== pueue --config status --json
{"tasks":{"0":{"id":0,"created_at":"2026-10-24T10:13:17.273859792Z","original_command":"coreutils_unused=1 /usr/bin/timeout -k 5 600 sh -c \"inotifywait ...
== ls workmux agents
-rw------- 1 agent agent  539 Oct 23 23:35 tmux__%2Ftmp%2Ftmux-1000%2Fdefault__%2510.json
== write test workmux
write ok
```

One `rc=134` on the no-`--config` call in B came from `head -c` closing the pipe (pueue panics on `Broken pipe`), not from a connection failure. fleetd must read pueue output fully.

Surprise: with `ProtectSystem=strict` alone, `/home` stayed writable.

```
== write test HOME (expect fail)
UNEXPECTED write ok
```

Confirmed with `systemd-run -p User=agent -p ProtectSystem=strict`: `touch /home/agent/p1` succeeds; `/etc` and `/var/tmp` are read-only. mountinfo shows `/home` as a separate `rw` bind. Adding `ProtectHome=read-only` makes `/home/agent` read-only, with `ReadWritePaths=/home/agent/.local/state/workmux` still writable, `agents/` listable and `pueue status --json` still working (rc=0).

Unit and journals cleaned up: unit file removed, `systemctl daemon-reload` run, `systemctl is-enabled fleetd-t9` returns `not-found`. Nothing enabled.

## Result

Pass. The unit reaches the pueue socket and reads and writes workmux state, with and without `XDG_RUNTIME_DIR`.

## Plan impact

- `XDG_RUNTIME_DIR` is not needed when `unix_socket_path` is absolute and the unit passes `--config` or has `HOME` set. Keep setting `XDG_RUNTIME_DIR=/run/user/1000` anyway: it costs nothing and covers a config that drops `unix_socket_path`. Keep `After=user@1000.service` (the socket lives in its tmpfs). Add `Wants=user@1000.service` so the dependency also starts it.
- `ProtectSystem=strict` does not protect `/home` on this box. The plan's "read-only access to `~/jobs`" is not enforced by it. Add `ProtectHome=read-only` plus `ReadWritePaths=` for the fleetd state dir and `~/.local/state/workmux`. Check `ReadWritePaths` also covers any worktree fleet-job must write: those need their own entry or a separate process.
- The `systemd-run --user` fallback in the plan risk table is not needed.
- Plan line 147 can say Verified on <box>.
- Handle pueue client `Broken pipe` panics: read the full output.
