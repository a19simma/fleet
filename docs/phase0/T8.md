# T8. Hook failure latency with fleetd down

Result: Pass. A refused connection costs about 1 ms and never fails the run.

## Question

With an http hook pointed at a closed port, how much does a `claude -p` run slow down, and does a failing hook break or block the run? A hang would mean a timeout must be set on the hook.

## Setup

Box: <box>, Claude Code 2.1.289, subscription auth. `ANTHROPIC_API_KEY` checked unset before every run. Files under `~/phase0/T8/` on <box>: `none.json` (`{}`), `closed.json` (http Stop hook to `http://127.0.0.1:18999/hook/Stop`, nothing listening), `closed_block.json` (same plus `"onFailure":"block"`), `closed_four.json` (http hooks for Stop, SessionEnd, Notification, UserPromptSubmit on the closed port). `run.sh <label> <n>` runs `claude -p --settings ~/phase0/T8/<label>.json --debug-file ... "reply with ok" --output-format json`. Results in `results.txt`, outputs and debug logs per run.

## Results (verbatim)

```
none run1 exit=0 wall=1.73868 dur_ms=1344 result=ok
closed run1 exit=0 wall=1.48886 dur_ms=1082 result=ok
none run2 exit=0 wall=1.59281 dur_ms=1157 result=ok
closed run2 exit=0 wall=1.73696 dur_ms=1132 result=ok
none run3 exit=0 wall=1.51134 dur_ms=1102 result=ok
closed run3 exit=0 wall=1.49587 dur_ms=1020 result=ok
closed_block run1 exit=0 wall=1.46437 dur_ms=1021 result=ok
closed_four run1 exit=0 wall=1.6129 dur_ms=1224 result=ok
```

Mean wall: no hook 1.61 s, closed-port hook 1.58 s. The difference is inside the run-to-run noise (about 0.2 s). The hook cost itself, from the debug log timestamps:

```
10:15:28.818Z Hooks: HTTP hook POST to http://127.0.0.1:18999/hook/Stop
10:15:28.820Z [ERROR] Hooks: HTTP hook error: connect ECONNREFUSED 127.0.0.1:18999
10:15:28.820Z [ERROR] "Hook Stop (Stop) error:\nstderr:\nconnect ECONNREFUSED 127.0.0.1:18999"
```

About 2 ms for the refused connect. With four http hooks (UserPromptSubmit and Stop attempted and logged, 1 to 2 ms each) the run took 1.61 s. I did not see a SessionEnd or Notification attempt in the closed_four debug log (SessionEnd at exit may not be logged before the process ends); not verified.

`onFailure: "block"` on a refused connection (closed_block): exit 0, `result` "ok", `is_error:false`, `terminal_reason:"completed"`. The same error was logged as for the plain hook, so on 2.1.289 the field has no observable effect: either it is ignored or a connection error never blocks. I did not find any warning about the unknown field.

## What claude does with a failing http hook

It logs the error at ERROR level in the debug log, continues, and returns the normal result. Nothing appears in stdout and the exit code stays 0. In `-p` mode there is no user-visible signal.

## Result

Pass. A down fleetd costs about 2 ms per hook and does not hang, slow or fail the run. This covers only connection refused on loopback. A reachable but slow or stalled listener (accepts then never answers) was not tested; for that case set an explicit `timeout` on the hook.

## Plan impact

- Hooks can point at the loopback port without a timeout for the fleetd-down case. Still set `timeout` on each http hook as a guard against a stalled fleetd (untested here), so the stalled case cannot hold a turn.
- ADR note ("Managed settings versus the baked settings.json stays an implementation detail, settled by T4 and T8"): T8 shows the baked `settings.json` hook is safe when fleetd is down. No reason to prefer managed settings on latency or failure grounds.
- Hook delivery is fire-and-forget with no retry: events sent while fleetd is down are lost. The plan needs a gap-detection or reconciliation story (for example fleetd re-reads transcripts or workmux state at start) if lost events matter.
- Drop `onFailure` from the plan's hook config on the 2.1.289 pin. It does nothing here and its semantics need 2.1.295 or later.
