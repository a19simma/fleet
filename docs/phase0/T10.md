# T10: transcript contents and drift

Result: **Partial**. The transcript is readable and carries `usage` and `model`, but it lags the `Stop` hook by up to 2 s and always misses the final assistant entry at hook time. Subagent token counts do not reconcile with the `result` message.

Environment: <box>, Claude Code 2.1.289, model `claude-sonnet-5-5`, subscription auth (`ANTHROPIC_API_KEY` confirmed unset before every run), 2026-10-24. Artifacts are under `~/phase0/T10/` on <box>.

## Question

What do the files at `transcript_path` contain, do assistant entries carry `usage` and `model`, do messages repeat by id, is `output_tokens` a placeholder, and how far does the file lag a `Stop` hook? Does the file agree with the `result` message?

## Setup

- `~/phase0/T10/settings.json` registers `Stop` and `SessionEnd` command hooks that run `~/phase0/T10/hook.sh <event>`. Passed with `claude --settings`. `~/.claude/settings.json` untouched.
- `hook.sh` writes stdin to `hooklog/<event>-<ns>.json`, copies the transcript to `.t0.jsonl` at hook time, sleeps 2 s, copies again to `.t2.jsonl`, and stamps `.time0` and `.time2`.
- Working directory: `/home/agent/phase0/T10/work`. Four Claude runs, one at a time, tiny prompts only.
- A first hook version backgrounded the 2 s copy with `setsid nohup`. In `claude -p` that copy never ran (the process tree is gone at exit), so the hook sleeps synchronously. On `SessionEnd` in `-p` the 2 s copy also does not happen (the process exits), only `.t0` exists.

## usage and model

Both present on every `assistant` entry. Example (reply run): `{"id":"msg_011CgLtFn1vdoQxJeCp2LYMA","model":"claude-sonnet-5-5","stop":"end_turn","usage":{"input_tokens":2,"output_tokens":4,"cache_creation_input_tokens":15252,"cache_read_input_tokens":17269}}`.

## Repeated ids

Yes. A message with a thinking block and a tool_use block is written as two `assistant` entries with the same `message.id` (tool run, main session):

```
{"uuid":"4fe664cf","id":"msg_011CgLtHamJZoRcAgkBRvYmW","stop":"tool_use","content":["thinking"],"out":174,"in":2}
{"uuid":"1a6752ea","id":"msg_011CgLtHamJZoRcAgkBRvYmW","stop":"tool_use","content":["tool_use"],"out":174,"in":2}
{"uuid":"3318689f","id":"msg_011CgLtJArfigFebVMgKHv2f","stop":"end_turn","content":["text"],"out":22,"in":2}
```

The entries have different `uuid` and one content block each. Sum of `output_tokens` over all entries is 370. De-duplicated by id it is 196, which equals `result.usage.output_tokens` (196). Summing without de-duplication double counts.

## output_tokens placeholder

Partly. Two sources differ for the same message id:

- stream-json `assistant` lines carry `output_tokens: 2` for `msg_011CgLtHamJZoRcAgkBRvYmW`. The transcript carries 174 for the same id. The stream value is a streaming-start placeholder; the transcript holds the final value for main-session messages.
- Subagent transcript entries (`isSidechain: true`, `stop_reason: null`) show `out` 16 and 24, the same placeholder-looking values as the stream (16 and 24). Main plus subagent totals 174 + 22 + 16 + 24 = 236, but `result.modelUsage["claude-sonnet-5-5"].outputTokens` is 415. `result.usage.output_tokens` (196) covers only the main session. So subagent transcripts undercount and per-step transcript tokens cannot be summed to a cost figure.

In the short single-message runs, transcript `output_tokens` (4) equals `result.usage.output_tokens` (4) and `modelUsage.outputTokens` (4).

## Lag behind Stop

The hook copied the transcript at hook time (`.t0`) and 2 s later (`.t2`).

| Run | lines at Stop | lines at +2 s | last entry at Stop | last assistant entry present at Stop |
|---|---|---|---|---|
| `-p` reply | 17 | 21 | `atis-latch` | No |
| `-p` tool | 27 | 28 | `atis-latch` | No: final text message `msg_011CgLtJArfigFebVMgKHv2f` missing |
| interactive reply | 21 | 28 | `ai-title` | No |

In every run the final `assistant` entry was absent at `Stop`, even though its `timestamp` was 23 ms (interactive: `10:14:30.410Z` vs hook at `1792836870.433`) to 22 ms (json run) before the hook fired. At +2 s the final entry is present. `SessionEnd` (read at hook time, about 2 s after `Stop`) contains the final assistant entry plus `system`, `last-prompt` and `cost-state`.

In the tool run, the `Stop` read contained the first two assistant entries but not the final answer. So the `last_assistant_message` field is the only reliable source of final text at `Stop`; the file catches up by `SessionEnd`.

## Result

Partial.

- Pass: `usage` and `model` exist on every assistant entry; the path format is stable; `cost-state` agrees with `total_cost_usd`.
- Fail for the plan as written: the file does not contain the final turn at `Stop`; `output_tokens` repeats per content block (needs de-dup by `message.id`); subagent entries have placeholder token counts and live in a different file.

## Plan impact

Transcript reader section:
- Keep the "later read wins" rule and make it concrete: a read at `Stop` is expected to be missing the final assistant entry. Read again on `SessionEnd`; consider a delayed re-read about 2 s after `Stop` for long-lived interactive sessions (the file had caught up by +2 s in all three runs).
- Add de-duplication by `message.id` for any token or message count. Prefer the last entry per id.
- Replace the unverified claims: repeated ids confirmed; the `output_tokens` placeholder is confirmed for streamed and subagent entries, not for main-session transcript entries.
- Subagent work lives under `<session_id>/subagents/`. Do not use it for tokens.
- Cost stays on the `result` message. The transcript `cost-state` entry is a corroboration, written after `Stop`.
- The `Stop` payload and transcript carry no marker of the final entry, so detect completeness by `stop_reason: "end_turn"` on the last assistant entry.

`transcript.summary` event:
- Must tolerate a missing final assistant entry; fall back to `last_assistant_message` from the hook for the preview text. Mark the summary with its source (`stop` or `session_end`).
- Do not put token or cost totals in it.
- Entry types to expect: listed above, with 11 `attachment` subtypes; ignore unknown types.

ADR-0012: record that the transcript is best-effort and lagging, that totals come from `result`, and that this was measured on 2.1.289 and must be re-run on any pin bump.

Not covered: very long turns, sessions with many tool calls, `--resume` file reuse, and lag under heavy disk load. Single sample per mode, so the lag figure is a lower bound (the transcript was complete at 2 s; the true catch-up point is between 0 and 2 s).
